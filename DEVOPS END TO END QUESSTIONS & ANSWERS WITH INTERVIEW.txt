❓Q1: A server is slow. What will you check first?
✅ Answer (Interview-Ready):
“First, I check CPU, memory, disk, and load using top, free, df, and uptime.
Then I identify which process is consuming resources.
I check application and system logs for errors.
If required, I analyze I/O using iostat.
Based on findings, I either tune the app, restart services, or scale resources.”

❓Q2: Production disk is full. Application stopped. What will you do?
✅ Answer:
“First, I check disk usage using df -h and du.
I identify large files or logs.
I rotate or delete unnecessary logs.
If required, I move files to backup storage.
Then I implement logrotate to avoid recurrence.”

❓Q3: How do you investigate memory leak?
✅ Answer:
“I monitor memory using free, top, and vmstat.
I identify processes with high RES memory.
I check application heap usage and GC logs.
If required, I take heap dump and share with dev team.
Meanwhile, I apply temporary restart or scaling.”
A memory leak occurs when an application continuously allocates memory but fails to release it after use. As a result, memory usage keeps increasing over time, which can degrade performance or crash the system. In production environments, we monitor memory usage and identify such issues using tools like top or monitoring platforms, and the development team usually fixes the root cause in the application code.

❓Q4: What is Load Average? How do you interpret it?
✅ Answer:
“Load average shows average number of runnable or waiting processes in 1, 5, and 15 minutes.
If load is higher than CPU cores, system is overloaded.
I correlate load with CPU and I/O metrics.”
Load average represents the average number of processes that are either running on the CPU or waiting for CPU resources. It is calculated over 1, 5, and 15 minute intervals and helps determine how busy a Linux system is.

❓Q7: What is Zombie process? How do you handle it?
✅ Answer:
“A zombie process is a completed process whose entry remains in process table.
It happens when parent doesn’t collect exit status.
I identify it using ps aux | grep Z.
Usually, restarting parent process clears it.
If many zombies appear, I investigate application bug.”
A zombie process is a process that has completed execution but still remains in the process table because its parent process has not yet read its exit status using the wait() system call. It does not consume CPU or memory but still holds a process ID until the parent process collects the status.

❓Q8: How do you analyze high disk I/O wait?
✅ Answer:
“I check %wa in top.
Then I use iostat -x to see device latency.
I find processes using iotop.
I check for heavy log writes, DB dumps, backups.
Then I optimize or schedule jobs off-peak.”

❓Q9: What is OOM Killer?
✅ Answer:
“OOM Killer is triggered when system runs out of memory.
Kernel kills high-memory processes to protect system.
I check dmesg and logs to confirm.
Then I tune application memory or add RAM/swap.”

❓Q3: Difference between merge and rebase?
✅ Answer:
“Merge preserves commit history.
Rebase rewrites commit history.
We use merge for shared branches.
We use rebase for local cleanup.”
Git merge combines two branches and creates a merge commit, preserving the full branch history. Git rebase, on the other hand, rewrites commit history by moving commits to the latest base commit, creating a linear history without an additional merge commit.

❓Q4: How do you revert a bad commit in production?
✅ Answer:
“If already pushed, I use git revert.
It creates a new commit to undo changes.
If not pushed, I use git reset.
Then I redeploy and monitor.”
 In production environments we avoid rewriting Git history. If a bad commit is deployed, we identify the commit using git log and safely revert it using git revert. This creates a new commit that reverses the changes. After pushing the revert commit, the CI/CD pipeline redeploys the stable version.

One Real Thing Good Engineers Mention
In critical production issues, we may also perform an immediate rollback to the previous stable artifact while reverting the commit in Git.

❓Q5: What is cherry-pick? When do you use it?
✅ Answer:
“Cherry-pick applies specific commits.
I use it to move hotfix from one branch to another.
Example: from develop to release.”
Cherry-pick in Git is used to apply a specific commit from one branch to another branch. It is typically used when we want to bring a particular change, such as a bug fix, into another branch without merging the entire branch.

❓Q6: How do you secure Git repositories?

Git repositories are secured using access control, branch protection rules, pull request reviews, and security scanning. Sensitive branches like main are protected to prevent direct commits, and all changes must go through pull requests and code reviews. Additionally, security tools such as SonarQube and Trivy are integrated into CI/CD pipelines to detect vulnerabilities and ensure secure code before deployment.
We also avoid storing sensitive data such as passwords or API keys in repositories and instead manage them using secure secret management mechanisms.
